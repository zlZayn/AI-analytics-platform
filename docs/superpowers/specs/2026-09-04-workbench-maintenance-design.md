# AI Analytics Platform 维护设计

## 目标

- 让“在工作台执行”从探索页和查询管理页稳定到达工作台并自动执行。
- 防止 Windows 启动入口在构建后继续复用旧的 `next start` 进程。
- 降低工作台、探索页、查询管理页的布局拥挤和状态不透明问题。
- 保持现有安全边界、会话驱动架构和亮色语义 token 不变。

## 范围

- 启动入口：`Start Dev.cmd` 的构建、旧服务处理、启动和健康检查。
- 页面跳转：统一生成 `/workspace` URL，保留 connection 与 URL 编码后的 SQL。
- 工作台状态：区分初始 SQL 注入、执行中、成功、失败和重试；不重复执行同一初始 SQL。
- 页面布局：只调整 workspace、explorer、queries 的空间分配、窄屏行为和操作反馈。
- 文档与验证：同步架构、实现状态、维护清单、子目录索引和离线 E2E。

## 设计

### 启动生命周期

`Start Dev.cmd` 保持单一入口和 GBK + CRLF + 无 BOM 格式。

- 新鲜度为 `STALE` 或 `NOT_BUILT` 且用户选择构建时设置重启标记。
- 构建成功后重新检查端口；如果已有服务，结束该 PID 并等待端口释放。
- 仅启动一个新服务实例，再执行健康检查和浏览器打开。
- 用户选择开发模式时不构建，保留现有服务复用行为。

### 工作台导航与执行

- 新增一个纯函数生成工作台 URL，所有跨页面入口使用相同编码规则。
- 工作台以 `connectionId + initialSql` 作为一次初始执行输入。
- 初始 SQL 只在挂载时注入一次，通过现有 `SET_COMPILED_SQL` 进入执行副作用。
- 初始 SQL 执行失败时保留编辑器内容、错误信息和手动重试能力。
- 未提供 connection 或 SQL 时不触发请求，不显示误导性的执行中状态。

### 布局与反馈

- 工作台使用明确的 SQL 操作区、AI 区和结果区比例；窄屏改为可滚动的纵向分区。
- 主操作按钮显示执行中禁用态，结果区显示加载、成功、空结果和错误状态。
- 探索页和查询管理页的执行入口保持统一尺寸、图标和可访问名称。
- 不新增颜色常量，不改变现有图表、数据库和 R 工作台的数据边界。

## 测试策略

- 启动脚本合同测试：构建后已有 PID 必须被重启；普通启动仍可复用运行中的服务。
- 导航纯函数测试：connection、SQL 空格、中文和特殊字符均正确编码。
- 工作台 E2E：探索页点击“在工作台执行”后断言 URL、编辑器 SQL、一次 `/api/query` 请求和结果渲染。
- 工作台 E2E：查询失败后断言错误可见且 SQL 保留。
- 常规验证：`npm test`、`npm run typecheck`、`npm run lint`、`npm run build`、离线 E2E、链接/换行/diff 检查。

## 替代方案

- 仅在按钮上增加 `window.location`：不能解决旧生产进程复用，也会绕开 App Router 状态管理。
- 继续叠加 `useEffect` 修补时序：短期可通过单一场景，但会增加重复请求和竞态风险。
- 把开发入口改成 PowerShell：可读性更高，但破坏现有双击入口和 Windows 用户习惯，本轮不采用。

## 影响

- 启动入口在构建后会主动重启当前端口服务，避免旧构建继续提供页面。
- 跨页面执行链有单一 URL 生成规则，减少参数丢失和编码差异。
- 视觉改动保持局部，现有 API、数据库、图表和 R 分析契约不变。
